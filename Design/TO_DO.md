===Main on 19 05 2026===

MLF - Malachite Language Frontend - предполагаемое API, которое позволит транслировать текст условного ЯП в последовательность IRCSH - Intermediate Representation Code Stack Handling - промежуточное представление кода стековой обработки. Данное API предоставляет (по задумке на данный момент): двухпроходной лексер с анализатором кодировок (он же CharacterAnalyzer), единую систему хранения информации TranslationContext, систему загрузки и обработки конфигов (на данный момент будет использовать ELDCL), функции и типы для работы с API. Предполагается, что TranslationContext, точнее его подсистема SemanticSystem, будет работать с Semantic units (символы, например, функции, типы и тд).

По сути, MLF - это скелет фронтенда, насадить на него мясо потребуется программисту с помощью обработчиков, скорее всего, будет использоваться ООП подход - классы обработчики(у наследованные от, например, IHandler), а не функции.



===Tokens types 19 05 2026===

MLF должен предоставлять такую систему токенов, чтобы можно было работать без особых затрат... То есть текст прогнать через лексер и с помощью внешней настройки (может... конфиги?) получить нужный/подходящий массив токенов.



Стандартные типы токенов следующие:

UNDEFINED = 0,		Токен не определён. По сути, заглушка (чтобы сделать часть пакета недействительной).

IDENTIFIER = 1,		Идентификатор, то есть любая последовательность символов, которая не относится к другим группам.



OPERATOR = 2,

Обычные операторы: +-\*/ и тд. Может ++ и тд. Выстраиваются через конфиг.

tag::operator Plus

{

Type: OBinary;

Identifier: "+";

Precedence: 10;		//Int, прямая пропорциональность, чем больше Precedence, тем больше приоритет

Associativity: LEFT;

}

tag::operator UnaryMinus

{

Type: OUnary;

Identifier: "-";

Precedence: 12;

Associativity: RIGHT;

}

tag::operator Ternary

{

Type: OTernary;

Identifier: "?";

PostIdentier: ":";

Precedence: 5;

Associativity: RIGHT;

}





META\_OPERATOR = 3, 	Метаоператоры: \[identifiervariable] to \[type], new \[Object] и тд. То есть те же ключевые слова to, new, но вынесенные в отдельную категорию.

LITERAL = 4,   		Строки и числа. Обрабатываются с помощью маски в конфиге.

LITERAL\_IDENTIFIER = 5, Идентификаторы для литералов: null, nullptr, true, false. Можно также не использовать, обрабатывать ключевые слова.

DELIMITER = 6,		Пробелы, табы, запятые и тд.

GENERAL\_KEYWORD = 7,	Обычные ключевые слова, например, ptr или const. Настройка через конфиг. По логике, обрабатываются стандартным (общим) AST строителем.

SYNTAX\_KEYWORD = 8,	Ключевые слова, обозначающие синтаксические конструкции: while, for, func и т.д.Настройка через конфиг.

TRANSLATION\_LABEL = 9	Маркер трансляции. Пока что неясно, для чего нужен.



Помимо стандартных типов планируется регистрация пользовательских через конфиги и специальную таблицу. Например, добавление маркера для функций компилятора.



tag::token\_types TokenTypes	//Название может быть любое, главное, чтобы tag совпадал

{

&#x09;GENERAL\_KEYWORD: \["const", "ptr"];

&#x09;COMPILER\_FUNCTIONS: \["@template","@type\_id"];

}



В MLF будет именно, что таблица типов токенов с функциями автоинкремента (класс/структура TokensTypesTable),а не enum. Основные типы будут внесены вручную в код самого MLF в функции инициализации (**однако есть нюанс**). После регистрации каждому типу присвоится своё число. Token будет содержать в качестве типа именно это число. Числовой идентификатор типа (например, для сравнения) можно будет получить с помощью функций доступа... Опять же, это для меня, как разработчика, нужно реализовать карту STRING\_LITERAL-TYPE \[ЧИСЛО], а не STRING\_LITERAL-TYPE \[СТРОКА].



//\*\*\*Важно\*\*\*//

Если хотите избежать лишних вычислений функций хеширования и просто сравнивать типы, как обычные числа, то создайте в файле конфигурации типов следующий блок:

tag::token\_types\_ids TokenTypesIDs	//Название может быть любое, главное, чтобы tag совпадал

{

&#x09;UNDEFINED: 0;

&#x09;LITERAL: 1;

&#x09;и тд.

&#x09;USER\_TYPE0: 10;

&#x09;USER\_TYPE1: 11;

}

**Вот и нюанс**: стоит указать все базовые типы, иначе, скорее всего, выскочит ошибка (или нет, скорее всего, тот же + будет помечен как UNDEFINED, ибо это уже дефолт-дефолт). Автоматическая регистрация в коде работать не будет (специально условие поставлю на обнаружение блока c tag::token\_types\_ids).

Зато в коде сможете использовать такой синтаксис:

if (token.type == 10) действие;

10, естественно, можно заменить на enum или макрос.









===ASTBuilding/Parsing 21 05 2026===

Так как MLF будет чем-то наподобие платформы, то мы не можем установить точную синтаксическую грамматику, что печально. Однако MLF предоставит API и стандарты (IRCSH и токены), единое хранилище frontend информации (TranslationContext).





Простые синтаксические конструкции, например, объявление переменной, лежат на ответственности пользователя. Единственное, что предоставляет MLF - это функции помощники и стандарт AST узлов. Для работы с операторами/стандартными вычислительными выражениями может быть использовал встроенный Pratt парсер, состоящий из двух частей: General и Syntax. Первый обрабатывает порядок операторов, а второй - вызовы функций, индексацию в массивах, их синтаксис, к сожалению пользователя будет стандартизирован, то есть вшит, нельзя будет сделать вызов функции таким: function->(arg0|. Только function(args). С индексацией также. Срезы и тому подобное будет уже реализовывать пользовательские обработчики кодогенератора или VM. Благо, у меня есть идея: добавить кастомные IRCHS команды. Класс PrattParser будет сам вызывать SyntaxPP при необходимости, general функции он будет исполнять сам, иначе тогда мне придётся настраивать их взаимодействие.


tag::syntax\_construction WhileCycle

{

Type: WHILE; //В динамическом enum заменяется на специфичный ID. Этот числовой ID и получает  AST. Привязка функций обработки в c++ коде делается с помощью хеш-карты, то есть по ключу WHILE. В процессе компиляции это позволит вызывать обработчики без сравнения. Шаблоны синтаксических конструкций вообще тогда не нужны.

Mask: "@while(MLF\_EXPRESSION) MLF\_STATEMENT";

AnotherInfo....

}

Парсер масок разбивает маску на токены с помощью лексера, а потом обрабатывает её, превращая в структуру MASK.

MLF\_EXPRESSION - маркер выражения, следовательно, не должно быть блоков кода и других синтаксических конструкций. Может включать в себя подвыражения....

EXPRESSION - это арифметические операции, вызов функции, операции с памятью (взятие указателя/разменование)

MLF\_STATEMENT - маркер утверждения, следовательно, может быть представлено блоком кода {} или одиночным утверждением, например, инкрементом переменной.

@while - обозначение опорного слова, то есть while

У метаоператоров:

tag::meta\_operator TypeConvertion

{

Mask: "MLF\_EXPRESSION @to #\[MLF\_GENERAL\_KEYWORD...MLF\_IDENTIFIER]";

}



У констант:

tag::literal Real32
